super() returns a proxy object that delegates method calls to the next class in the MRO. It lets you call a parent method without hardcoding the parent class name.


 •   Why super() over ParentClass.method(self)
If you rename the parent class, super() still works - no change needed. super() follows MRO correctly in multiple inheritance.
Hardcoding the parent name (Animal.speak(self)) breaks in diamond inheritance.

Duck typing is Python's approach to polymorphism without inheritance. If an object has the methods and attributes you need, you can use it - regardless of its class.

"If it walks like a duck and quacks like a duck, then it is a duck."

You don't check IS-A relationships. You just call the method. If it works, great. If not, you get an AttributeError.

Duck typing - no inheritance required:

Traditional Type CheckingDuck TypingChecks actual class/type firstChecks behaviour (can it do the thing?)Uses isinstance() or type()Just calls the methodWorks with class hierarchiesWorks with ANY object that fitsMore restrictive - needs inheritanceFlexible - no inheritance required

Encapsulation means keeping internal data safe and hidden from outside code. Python uses naming conventions (not hard enforcement) to signal access levels.


PrefixNameConvention MeaningPython EnforcementNo prefixPublicAnyone can accessNone - open access_singleProtectedInternal use; subclasses OKConvention only - Python allows access doublePrivateClass internal onlyName mangling - Python renames it

Public, Protected, Private - Full Demo	
All three access levels in one class:
class BankAccount:

self.owner	= owner	# public - accessible anywhere
self._log	= []	# protected - for internal / subclass use

_BankAccount balance

def deposit(self, amount): self. balance += amount
self._log.append(f'+{amount}')

@property lets you access a method like an attribute - without calling it with parentheses. It turns a method into a read-only (or read-write) computed attribute.

@property - expose private data safely:
class Temperature:def  init (self, celsius):self. celsius = celsius	# private storage@propertydef celsius(self):	# getter - called as obj.celsiusreturn self. celsius@propertydef fahrenheit(self):	# computed property - no separate storagereturn self. celsius * 9/5 + 32t = Temperature(100)print(t.celsius)	# 100	- no parentheses neededprint(t.fahrenheit)	# 212.0 - computed on the flyt.celsius = 25	# AttributeError - no setter defined yet# 100
# 212.0
# AttributeError: can't set attribute






@property.setter lets you intercept assignment (obj.attr = value) and run validation or transformation before storing the value. You must define a getter with @property first.

@property + @setter - full pattern:
class Student:
def  init (self, name, age):
self.name = name	# uses the setter below automatically
self.age = age	# uses the setter below automatically

@property
def name(self):
return self. name

@name.setter
def name(self, value):
if not isinstance(value, str) or len(value.strip()) == 0: raise ValueError('Name must be a non-empty string')
self. name = value.strip().title()

@property
def age(self):
return self. age

@age.setter
def age(self, value):
if not isinstance(value, int) or not (0 < value < 150): raise ValueError(f'Invalid age: {value}')
self. age = value

@property
def profile(self):	# computed, read-only property
return f'{self.name} (age {self.age})'

s = Student('alice smith', 21)
print(s.name)	# Alice Smith - auto-formatted
print(s.age)	# 21
print(s.profile)	# Alice Smith (age 21)
s.age = 200	# ValueError: Invalid age: 200
# Alice Smith # 21
# Alice Smith (age 21)
# ValueError: Invalid age: 200

Abstraction means showing only what is necessary and hiding the details. In Python, formal abstraction is implemented with the abc (Abstract Base Classes) module. It lets you define a blueprint (interface) that child classes MUST implement.


Basic ABC Example	
Defining and using an abstract base class:
from abc import ABC, abstractmethod

class Shape(ABC):	# abstract base class
@abstractmethod
def area(self):	# abstract method - MUST be overridden
pass

@abstractmethod
def perimeter(self): pass

def describe(self):	# concrete method - shared by all
return f'Area={self.area():.2f}, Perimeter={self.perimeter():.2f}'

class Circle(Shape):
def  init (self, r): self.r = r
def area(self):	return 3.14159 * self.r ** 2 def perimeter(self):	return 2 * 3.14159 * self.r

class Square(Shape):
def  init (self, s): self.s = s
def area(self):	return self.s ** 2 def perimeter(self):	return 4 * self.s

print(Circle(5).describe()) print(Square(4).describe())

s = Shape()	# TypeError - cannot instantiate ABC
# Area=78.54, Perimeter=31.42 # Area=16.00, Perimeter=16.00
# TypeError: Can't instantiate abstract class Shape with abstract methods area, perimeter

SOLID is a set of five design principles introduced by Robert C. Martin (Uncle Bob). They guide how to write OOP code that is easy to maintain, extend, and test.


SSingle Responsibility Principle - A class should have only ONE reason to change
Every class should do exactly one thing. If you find yourself writing 'and' when describing what a class does, it has too many responsibilities.
? Wrong: class UserManager handles login AND sends emails AND logs to DB
 ? Right: class UserAuthenticator, class EmailService, class UserLogger - one each
SRP - before (violation) and after (fixed):

OOpen/Closed Principle - Open for extension, closed for modification
You should be able to add new behaviour by writing new code - not by editing existing, tested code. Achieve this with inheritance and abstraction.
? Wrong: adding a new shape requires editing the existing area calculator function
 ? Right: each shape implements its own area() - add new shapes without touching old code
OCP - closed to modification, open to extension:


LLiskov Substitution Principle - Subclasses must be substitutable for their parent class
Any code that works with a Parent should work equally well with a Child - without knowing it is a Child. A subclass must not remove functionality or change semantics.
 ? Wrong: Square extends Rectangle but breaks setWidth()/setHeight() because a square keeps both equal
 ? Right: Shape ? Rectangle and Shape ? Square independently, without violating each other's contract
LSP - violation and fix:



IInterface Segregation Principle - No class should be forced to implement methods it does not need
Split large interfaces into smaller, specific ones. A class should only implement what it actually needs.
 ? Wrong: a huge Printer interface forces all printers to implement scan(), fax(), and staple()
 ? Right: Printable, Scannable, Faxable as separate interfaces - BasicPrinter only implements Printable
ISP - split interfaces:

DDependency Inversion Principle - Depend on abstractions, not on concrete implementations
High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces/ABCs). This makes code flexible and easy to swap.
 ? Wrong: class ReportGenerator directly creates a MySQLDatabase() inside - hardcoded dependency
 ? Right: ReportGenerator depends on a Database ABC - any database can be injectedDIP - dependency injection via abstraction:
from abc import ABC, abstractmethod

# ? VIOLATION - tightly coupled to MySQL class ReportGeneratorBad:
def  init (self):
self.db = MySQLDatabase()	# hardcoded - impossible to swap

# ? CORRECT - depends on abstraction class Database(ABC):
@abstractmethod
def query(self, sql): pass

class MySQLDatabase(Database):
def query(self, sql): return f'MySQL: {sql}'

class PostgresDatabase(Database):
def query(self, sql): return f'Postgres: {sql}'

class ReportGenerator:
def  init (self, db: Database):	# depends on abstraction, not concrete
self.db = db
def generate(self, query): return self.db.query(query)

r1 = ReportGenerator(MySQLDatabase())
r2 = ReportGenerator(PostgresDatabase()) print(r1.generate('SELECT *')) print(r2.generate('SELECT *'))
# MySQL: SELECT *
# Postgres: SELECT *


PrincipleOne-line RuleKey TechniqueS - Single ResponsibilityOne class, one reason to changeSplit classes by responsibilityO - Open / ClosedOpen for extension, closed for modificationInheritance + abstractionL - Liskov SubstitutionSubclass must fully replace parentKeep the contract - don't weakenI - Interface SegregationDon't force unused method implementationsMultiple small ABCs over one big oneD - Dependency InversionDepend on abstractions, not concretesInject dependencies via ABC
